# Kanleaf v0.1 Rewrite Design

Date: 2026-08-26
Status: approved

## Purpose

Kanleaf v0.1 is a self-hostable desktop project manager that combines structured
workspace, project, and task data with durable Markdown documents. The rewrite
replaces the existing Dioxus application with a React frontend in Tauri v2 and a
standalone Axum server backed by PostgreSQL and a filesystem vault.

The release is successful when a new user can connect a desktop client to a
server, register, organize tasks across workspaces and projects, edit a task's
Markdown document, restart the system, and recover both the task metadata and
the exact Markdown source.

## Scope

The v0.1 product includes:

- server URL configuration and health validation;
- email/password registration, login, logout, and expiring sessions;
- personal workspace creation during registration;
- workspace creation, listing, switching, and renaming;
- project creation, listing, renaming, navigation, and archiving;
- Inbox and project task lists;
- task creation, title, status, priority, project movement, search, and archiving;
- a three-pane desktop workspace with keyboard-efficient navigation;
- Markdown source editing with edit, preview, and split modes;
- explicit save, debounced autosave, and visible save status;
- filesystem Markdown documents identified by stable task IDs;
- Docker Compose self-hosting, automated tests, and CI quality checks.

The release deliberately excludes offline caches, synchronization, real-time
collaboration, attachments, labels, enterprise permissions, plugin systems,
custom workflows, and release automation. These require product decisions that
the core workflow does not yet justify.

## Repository and dependency structure

The rewrite uses an orphan branch named `rewrite/react-tauri`. The previous
implementation remains recoverable from the `archive/pre-react-rewrite` tag and
existing remote branches. No remote history is rewritten.

```text
kanleaf/
├── apps/
│   ├── desktop/          React, TypeScript, Vite, and the Tauri v2 shell
│   └── server/           Axum application, migrations, and server tests
├── docs/                 Architecture and contributor documentation
├── infra/self-host/      Production-oriented Docker Compose configuration
├── .github/workflows/    Continuous integration
├── Cargo.toml            Rust workspace
├── package.json          pnpm workspace commands
└── pnpm-workspace.yaml
```

Only `apps/server` and `apps/desktop/src-tauri` are Rust workspace members.
There is no shared `core` crate in v0.1: domain rules have only one real caller,
and extracting them would create an abstraction without demonstrated reuse.

Dependencies flow inward:

```text
React UI  -> HTTP API
HTTP      -> application operations -> domain rules
                                 |-> PostgreSQL persistence
                                 `-> filesystem vault
Tauri     -> hosts the React bundle and exposes no business logic
```

The server remains one crate. Modules express responsibility boundaries without
creating traits for adapters that have only one implementation. Domain types and
validation do not depend on Axum, SQLx, Tokio, Tauri, or filesystem APIs.

## Server architecture

The Axum application owns these cohesive areas:

- `config`: validates environment variables and produces startup configuration;
- `domain`: IDs, task status and priority, normalized email, and validation rules;
- `auth`: password hashing, session-token generation, authentication extraction;
- `workspace`, `project`, and `task`: use-case functions and their SQL operations;
- `vault`: typed task-document reads and atomic writes beneath the data root;
- `http`: thin request/response types, routes, and consistent error translation;
- `state`: the PostgreSQL pool, vault root, clock-independent configuration, and
  shared application state.

Handlers deserialize input, invoke one use case, and serialize its result. SQL
stays in the owning feature module, not in handlers. Multi-record invariants use
transactions. Database constraints enforce uniqueness, foreign-key ownership,
valid enum-like values, and nonempty normalized fields.

All JSON errors use a stable shape:

```json
{
  "error": {
    "code": "validation_error",
    "message": "Task title cannot be empty"
  }
}
```

Expected domain failures map to suitable 4xx responses. Unexpected errors are
logged server-side with a request identifier and returned as a generic 500
response without database or filesystem details.

## Database model

Ordered SQLx migrations create the following tables:

### `users`

- UUID primary key
- normalized email with a unique constraint
- password hash
- optional active workspace UUID
- created and updated timestamps

### `workspaces`

- UUID primary key
- name
- created and updated timestamps

### `workspace_memberships`

- workspace UUID and user UUID composite primary key
- role constrained to `owner` or `member`
- created timestamp

The two roles support ownership without introducing configurable RBAC. v0.1
does not expose member administration.

### `sessions`

- UUID primary key
- user UUID
- SHA-256 session-token hash with a unique constraint
- expiry and creation timestamps

Expired sessions fail authentication. Logout deletes the current session. Raw
bearer tokens exist only in the registration/login response and client-local
storage; they are never stored in PostgreSQL or logs.

### `projects`

- UUID primary key
- workspace UUID
- name
- nullable archived timestamp
- created and updated timestamps
- unique active name within a workspace

### `tasks`

- UUID primary key
- workspace UUID
- nullable project UUID
- title
- status constrained to `todo`, `in_progress`, or `done`
- priority constrained to `none`, `low`, `medium`, or `high`
- nullable archived timestamp
- created and updated timestamps

A composite foreign key ensures a task cannot reference a project from another
workspace. Inbox is represented solely by `project_id IS NULL`.

Registration runs one transaction that inserts the user, personal workspace,
owner membership, active workspace, and hashed session. A failure at any step
rolls back the complete registration.

## HTTP API

The JSON REST API is versioned under `/api` for v0.1:

```text
GET    /api/health
POST   /api/auth/register
POST   /api/auth/login
POST   /api/auth/logout
GET    /api/session

GET    /api/workspaces
POST   /api/workspaces
PATCH  /api/workspaces/:workspace_id
POST   /api/workspaces/:workspace_id/activate

GET    /api/workspaces/:workspace_id/projects
POST   /api/workspaces/:workspace_id/projects
PATCH  /api/workspaces/:workspace_id/projects/:project_id
DELETE /api/workspaces/:workspace_id/projects/:project_id

GET    /api/workspaces/:workspace_id/tasks
POST   /api/workspaces/:workspace_id/tasks
GET    /api/workspaces/:workspace_id/tasks/:task_id
PATCH  /api/workspaces/:workspace_id/tasks/:task_id
DELETE /api/workspaces/:workspace_id/tasks/:task_id

GET    /api/workspaces/:workspace_id/tasks/:task_id/document
PUT    /api/workspaces/:workspace_id/tasks/:task_id/document
```

Project and task `DELETE` operations archive records rather than physically
deleting them. Task listing accepts `project_id`, `inbox`, and `query` filters.
All nested resource queries include the authenticated workspace boundary. A
guessed UUID cannot reveal whether an inaccessible resource exists.

## Authentication and authorization

Email addresses are trimmed and lowercased before storage and lookup. Passwords
are hashed with Argon2id using fresh random salts. CPU-heavy password work runs
outside Tokio's asynchronous executor. Registration and login return a secure
random bearer token with at least 256 bits of entropy.

Authentication hashes the supplied bearer token with SHA-256 and looks up the
unexpired session. Authorization then checks membership before querying or
mutating workspace resources. Vault authorization is completed before any path
is constructed or filesystem operation begins.

The server accepts an explicit CORS origin configuration for browser-based
development. Self-host deployments do not default to an unrestricted wildcard
combined with credentials. Tokens use the `Authorization` header rather than
cookies, avoiding cross-site cookie and CSRF ambiguity for arbitrary server
URLs in the desktop client.

## Markdown vault

Structured task state remains in PostgreSQL. Markdown body content exists only
as an ordinary UTF-8 file:

```text
KANLEAF_DATA_DIR/
└── vaults/
    └── <workspace-id>/
        └── Tasks/
            └── <task-id>.md
```

Workspace and task IDs are parsed UUID values. The server constructs every path
from those typed values and never accepts an arbitrary path from an API caller.
Creating a task also creates an empty document. If document creation fails, the
task transaction is rolled back; if rollback cleanup fails, the orphan empty
file is harmless and can be reused by a later retry.

Document writes preserve the submitted bytes exactly. The vault writes a
temporary sibling file, flushes it, and atomically replaces the destination so
a crash cannot leave a partially written document. Task and project renames do
not move or rewrite Markdown. Kanleaf adds no frontmatter and creates no editor-
specific directories.

Concurrent collaborative conflict detection is deferred. The editor sends the
whole document, and the last successful save wins. This limitation is explicit
because v0.1 is a personal and small-team self-hosted release rather than a
collaborative editor.

## Desktop application

The desktop package is a normal browser-renderable Vite application hosted by a
minimal Tauri v2 shell. Tauri configures the window, bundle metadata, and CSP;
it does not duplicate server use cases or persist business state.

React code is organized by feature:

```text
src/
├── app/                  routing, providers, and application shell
├── components/ui/        small reusable controls with real cross-feature use
├── features/
│   ├── auth/
│   ├── workspace/
│   ├── project/
│   ├── task/
│   └── markdown/
├── lib/
│   ├── api/              fetch client and API error handling
│   └── config/           build-time server configuration
├── styles/               tokens and global layout styles
└── main.tsx
```

TanStack Query owns remote cache and mutation invalidation. Local storage
contains only the current bearer token, theme preference, and UI choices such
as Markdown view mode. Server-backed entity state is not mirrored into a custom
global store.

Vite embeds `VITE_KANLEAF_SERVER_URL` from the root `.env`. Startup validates
the HTTP or HTTPS URL, removes a trailing slash, and calls `/api/health` before
authentication. Network failures show the configured address and allow retry;
changing servers requires rebuilding or restarting with updated configuration.

## Interaction and visual design

The authenticated layout uses three panes:

1. a compact navigation pane for workspace selection, Inbox, projects, search,
   and settings;
2. a collection pane containing toolbar controls and dense task rows;
3. a detail pane containing editable task metadata and the Markdown document.

Task rows are flat list rows separated by subtle rules. The selected row uses a
strong but restrained accent background. Metadata uses compact text and icons,
not a collection of decorative pills. Empty, loading, and error states occupy
their natural pane rather than appearing as dashboard cards.

CSS custom properties define background levels, text colors, borders, accent,
danger, focus rings, radii, spacing, fonts, and control sizes. The initial theme
supports light and dark system preferences. Pane sizes use a desktop-first CSS
grid with minimum widths and a narrow-window fallback that hides navigation or
collection behind explicit controls instead of allowing horizontal overflow.

Keyboard behavior includes:

- `Ctrl/Cmd+S` to save Markdown;
- `Ctrl/Cmd+K` to focus task search;
- `N` to create a task when focus is not in a text field;
- arrow-key movement through task rows;
- Escape to return focus from detail to the selected task row.

Buttons, inputs, menus, and dialogs use semantic elements, visible focus rings,
accessible labels, and predictable tab order. Context menus use Radix primitives
only where native elements cannot provide correct keyboard behavior.

## Markdown editor and preview

CodeMirror 6 provides source editing, selection, cursor behavior, keyboard input,
history, and undo/redo without converting Markdown into a rich-text model.
`react-markdown` with `remark-gfm` renders CommonMark-style Markdown, task lists,
tables, and fenced code blocks. Raw HTML is not enabled; a sanitization stage is
kept in the render pipeline as defense in depth.

The detail pane offers Edit, Preview, and Split modes. Split mode shows source
and rendered content side by side with matching scroll containers. The editor
tracks the last server-confirmed source:

- unchanged content displays `Saved`;
- edits display `Unsaved` then `Saving` after an 800 ms debounce;
- successful writes update the confirmed source and display `Saved`;
- failures retain the edited source and display an actionable error;
- explicit save cancels the debounce and writes immediately.

Closing or switching away from a task with a failed or pending save requires a
confirmation. Successful autosave does not interrupt navigation.

## Testing strategy

Domain unit tests cover normalization, validation, status/priority parsing, and
cross-entity invariants without a database or filesystem.

PostgreSQL integration tests use isolated databases through SQLx test support
and checked-in migrations. They cover registration atomicity, password/session
behavior, workspace membership, active workspace changes, project ownership,
task filters and movement, archiving, and cross-workspace access denial.

Vault tests use temporary directories and cover deterministic paths, creation,
faithful UTF-8 round trips, atomic replacement, missing files, and authorization
ordering at the application boundary.

Vitest and React Testing Library cover connection validation, authentication
flows, task selection and editing, mutation errors, keyboard shortcuts, Markdown
mode changes, autosave state, and safe preview rendering.

Playwright runs the browser-renderable frontend against the real server and
PostgreSQL. Its core workflow configures a server, registers, creates and
switches workspaces, creates a project and task, moves the task, edits metadata,
writes and previews Markdown, reloads, and verifies persistence. A second user
scenario verifies workspace isolation. CI provisions PostgreSQL and a temporary
vault directory.

## Configuration and self-hosting

The server reads:

- `DATABASE_URL` (required);
- `KANLEAF_DATA_DIR` (required in production, development default documented);
- `KANLEAF_BIND_ADDRESS` (default `127.0.0.1:3000`);
- `KANLEAF_CORS_ORIGINS` (comma-separated allowed origins);
- `KANLEAF_SESSION_TTL_DAYS` (default 30);
- `RUST_LOG` (standard tracing filter).

The Docker image runs migrations at startup, then starts the server. Compose
contains only Kanleaf and PostgreSQL, uses a database health check, and mounts a
configurable host data directory so PostgreSQL data and Markdown vaults persist
under the deployment root. Secrets are supplied through environment variables
and an uncommitted `.env` file; `.env.example` contains safe development values.

## Delivery sequence

Commits remain capability-sized and independently coherent:

1. repository/workspace foundation and Tauri React scaffold;
2. Axum configuration, health endpoint, and PostgreSQL migration foundation;
3. authentication and registration;
4. workspace and project management;
5. task metadata workflow;
6. filesystem vault and Markdown API;
7. desktop connection/authentication shell;
8. workspace, project, and task UI;
9. Markdown editor, preview, and autosave;
10. UI refinement, accessibility, and narrow-window behavior;
11. integration and end-to-end coverage;
12. self-hosting, CI, and contributor documentation;
13. final audit fixes.

Before each commit, affected code is formatted, linted, tested, reviewed for
unrelated changes, and scanned for template leftovers. The final audit runs the
complete suite, starts and visually inspects the application, scans for deferred
markers and unsafe request-path panics, reviews dependencies and comments, and
confirms a clean working tree and readable history.

## Alternatives considered

A reusable Rust domain crate was rejected because the desktop talks to the
server over HTTP and has no Rust domain consumer. A local SQLite database and
sync subsystem were rejected because they introduce unresolved authority and
conflict semantics. A rich-text document framework was rejected because source
fidelity is central to the product. A broad component framework was rejected in
favor of CSS, semantic HTML, and a few focused interaction dependencies.

These decisions keep v0.1 small enough to finish while leaving later extraction,
offline caching, and collaboration possible when concrete requirements exist.
