# Webhooks V1 implementation design

Workspace webhooks are managed by current Owners/Admins through authenticated
internal endpoints. They are not personal resources or a public API.

## Persistence and events

`domain_events` stores an explicitly serialized V1 envelope and immutable request
body. `domain_event_outbox` records work per consumer; the first consumer is
`webhooks`. Both rows are inserted in the owning business transaction. Dispatch
locks unprocessed outbox rows with `SKIP LOCKED`, matches enabled subscriptions
and project scope, creates independent deliveries, and marks consumption in one
transaction. A unique webhook/event pair prevents duplicate dispatch.

The initial catalog is task created/updated/deleted and comment
created/updated/deleted. Task updated covers direct structured edits, bulk edits,
and archive, not Markdown-only saves, relations, ordering, or configuration
fan-out. Inbox events are excluded. Permanent task deletion preserves a curated
pre-deletion snapshot; comment deletion excludes the removed body. Project
identity is captured under the mutation's task lock rather than trusting an
earlier access lookup. Events never leave a rolled-back transaction.

Existing PostgreSQL/vault ordering and compensation remain intact. Metadata and
events commit together; filesystem operations cannot join that transaction.
Existing Task move/trash crash windows remain a vault limitation. A projection
failure after metadata commit does not undo its event. Realtime publishing stays
independent and unchanged.

## Secrets and delivery

An optional, explicit 32-byte base64 instance key enables webhook management and
delivery. A domain-separated HMAC of workspace ID, webhook ID, and a random
32-byte nonce derives each signing secret. PostgreSQL stores the nonce and key
fingerprint, not the secret. Missing configuration disables webhook operations;
invalid configuration or a changed key with existing webhooks fails startup.
Regeneration replaces the nonce. Creation/regeneration return a secret once.

Four worker loops claim one delivery each with a PostgreSQL row lock held across
the bounded request. `SKIP LOCKED` permits other processes/workers to progress;
rollback after a crash leaves work retryable. A per-webhook transaction advisory
lock prevents a slow endpoint backlog from occupying all workers. No expiring lease can overlap a
still-running attempt. Delivery IDs and exact bodies remain stable across
retries. Attempts use current configuration; an already-running request may
finish when a webhook is disabled or its secret regenerated. Disabled queued
deliveries are canceled, not resumed on re-enable.

Each request resolves and validates its destination, pins those addresses in
the HTTP transport while preserving hostname/TLS verification, disables
redirects, proxies, and transport retries, and bounds DNS/connect/total time.
Default policy rejects non-public destinations; private-network and HTTP
permissions are separate explicit instance settings. Response bodies are never
retained. Six attempts use delays of 30 seconds, 2 minutes, 10 minutes, 1 hour,
and 6 hours. Test events use the same durable delivery path and return a safe
result when completed, or a pending result for frontend polling.

## Product and contract

List, creation, and detail are routed Developer pages. Configuration reuses
form/list/dialog primitives. A creation result shows the secret in transient
component memory, never in route state or storage. Detail permits edit, test,
regenerate, and delete, and shows recent deliveries. Workspace switching from
detail/new returns to the target Workspace's webhook list.

Payload examples come from the authoritative backend envelope/data constructors
through a catalog endpoint. Create/Edit selects only subscribed preview events,
shows read-only formatted JSON and placeholder request headers, and copies only
the body. Serializer and contract fixture tests guard preview/documentation
drift. Back to Workspace moves into the sidebar footer above the account control.

## Verification

Behavior tests cover roles/revocation/tenant boundaries, input validation,
secrets/signatures, resolved-address policy, dispatch/claims/retries/restarts,
event producers/rollback, cascading deletion, frontend forms/routes/preview,
and footer layout. A controlled local receiver supports essential browser
coverage. Full Rust/frontend/build/PostgreSQL/browser/self-host checks and a
security-focused code review precede scoped commits, push, and CI verification.
